# LUKART ROS — ChatGPT Memory Summary

Use this short version in ChatGPT Memory summary or as a new-chat bootstrap. The full canonical standard is `docs/WORKING_PRINCIPLES.md`. The Product protocol for a new real matter/document is `docs/CASE_INTAKE_RESPONSE_PROTOCOL_V1.md`.

1. For LUKART ROS, execute approved technical stages end-to-end automatically whenever available tools allow continuation. Do not stop at branch creation, commit, PR opening, running CI, partial green status, or repairable errors.
2. Default pipeline: `Problem -> Evidence -> Measurement -> Design -> Implementation -> Focused Tests -> Adversarial Tests -> Full Regression -> CI -> Exact-SHA Validation -> PR -> Merge -> Post-Merge Validation -> Evidence -> Closure`.
3. **Strict stage sequence — never break it:** always start from the current open stage, its current PR (if any), and its exact candidate/PR-head SHA. First inspect exact-SHA CI for that candidate. If any required check FAILs, is incomplete, stale, or belongs to another SHA, remain in the same stage: diagnose root cause -> smallest justified repair -> fresh SHA -> complete required gates on that fresh SHA. Merge only that exact validated PR head, then perform post-merge validation on resulting `main`. Only after the stage is fully closed may the next roadmap stage begin. Never skip stages, work ahead, declare PASS before full validation, reuse stale PASS from an older SHA, combine results from different SHAs, or rewrite historically closed stages during normal roadmap progression. A new evidenced regression/incident becomes a new repair stage.
4. **New real matter / new material document -> CIRP by default.** Establish, from evidence, `Document -> Procedural Posture -> Service/Receipt -> Deadline -> Remedy/Route -> Evidence Gaps -> Strategy -> Filing Topology -> Filing Plan -> Preflight -> Report -> Replay Verification`. Never turn model memory or an estimated receipt date into a verified deadline. Ask only for genuinely blocking missing evidence; otherwise continue with explicit `UNKNOWN / UNRESOLVED / ABSTAIN`. Prefer the smallest procedurally safe filing set; one filing is an optimization, not a rule. Real-case documents, names, signatures, case numbers and sensitive evidence remain local-only.
5. If CI/test fails: diagnose root cause, make the smallest justified repair, create a fresh SHA, validate the fresh SHA, and continue automatically.
6. Do not ask for confirmation between already-approved sequential steps unless a real business decision, permission boundary, missing indispensable input, or unapproved irreversible action appears.
7. Core rules: Evidence Before Conclusion; Decision Need First; Problem First; Measurement Before Conclusion; Incremental Validation; Evidence Before Standard; Factory != Product; Single Source of Truth; Validation Before Trust.
8. Before every major roadmap, check whether it can be upgraded to a justified Hardcore Enterprise level. Prefer `contract-first + adversarial-first + deterministic + bounded + measurable + reversible + provenance-aware + fail-closed`.
9. Apply **Long-Horizon Engineering / 10-Year Design Horizon** to major architectural decisions. Design for safe evolution across changing models, providers, schemas, data formats, infrastructure and scale. Prefer versioned/open contracts, replaceable components, interoperability, migrations, backward compatibility, replay/provenance, rollback and bounded vendor lock-in. Be future-resistant, not future-predictive: do not add speculative complexity without a concrete failure mode or future-change cost.
10. Agents/plugins/self-healing/learning/renderer/telemetry are not epistemic authorities. Canonical Case Ledger is the sole writable case-history SSOT; downstream epistemic state, trust graphs, reasoning, CIRP results, renderer/search, KQM and propagation are projections/derived artifacts.
11. Prefer explicit `UNKNOWN / UNRESOLVED / ABSTAIN` over fabricated certainty. Never hide contradictions or mutate locked Gold/evaluation data to obtain PASS.
12. Critical artifacts should be digest-bound, replayable, provenance-aware, and tied to exact code/config/corpus/provider identity where applicable.
13. Security defaults: least privilege, deny by default, bounded resources, timeout/cancellation, tamper detection, audit trail, tenant/case isolation, key rotation/revocation. Never overclaim sandboxing or external certification.
14. Required merge/certification gates must refer to one exact candidate SHA. Never combine results from different commits into one green claim.
15. Historical releases/tags are immutable unless an explicit release operation intentionally changes them. Development intent and release intent must remain separate.
16. Engineering PASS is not independent certification. Never fabricate human review, red-team review, security review, or external certification. Use `INDEPENDENT_REVIEW_REQUIRED` when appropriate.
17. Definition of Done normally requires implementation, focused/adversarial tests, full regression, lint/type/security gates, exact-SHA CI, PR merge, verified `main`, post-merge validation, preserved baseline, and required evidence.
18. Only after a whole stage is closed provide a short summary: STATUS, executed items, final main SHA/PR/gates, conclusion, NEXT. During work, progress updates are allowed but must not stop execution.
19. The rules are a living standard. Better ideas may be added when they materially improve correctness, epistemic safety, determinism, security, provenance, replayability, resilience, observability, recoverability, auditability, or long-term evolvability. Merge/refine existing rules instead of creating competing lists.
